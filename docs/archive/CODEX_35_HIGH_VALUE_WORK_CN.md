# Codex 3.5 在本项目中的高价值工作方式

本文档说明：在 `msp` 项目里，什么类型的工作最能发挥 Codex 3.5 的优势，以及对应的落地示例。

## 1. 端到端问题闭环（定位 -> 修复 -> 验证 -> 文档 -> 发布）

最能体现优势的，不是单点改代码，而是完整闭环执行。

典型闭环：
1. 复现问题与日志归因。
2. 精准修改最小必要代码。
3. 增补回归测试。
4. 同步更新主仓库文档与 Wiki。
5. 推送并触发发布流程。

项目内示例：
- 播放器出现 `TypeError: c is not a function` 时，不只修 JS 一处，还应同时：
  - 修正变量遮蔽与错误处理路径。
  - 验证 `mp4` 正常直连、`wmv` 正确处理。
  - 更新 `CHANGELOG.md`、`docs/release/*.md`、`msp.wiki/Encoding*`。

## 2. 低侵入重构与兼容性精修

Codex 3.5 的优势在于：在不破坏现有行为的前提下，做可证明的优化。

优先策略：
- 保持接口与配置向后兼容。
- 避免重复造轮子，复用现有模块和工具函数。
- 仅修改必要文件，控制改动半径。

项目内示例：
- 播放策略优化为“探测感知 + 直连优先 + 单次回退”时：
  - 不引入新配置项。
  - 复用现有 `/api/probe` 结果与前端缓存。
  - 仅对高风险容器/编码预转码，不把可直连媒体误导向转码。

## 3. 跨层协同（前端 + 后端 + 配置 + 文档）

本项目是 Go 后端 + Web 前端 + 配置驱动 + Wiki 文档并行演进，适合 Codex 做跨层一致性治理。

高价值点：
- 前端播放行为与后端 MIME/探测结果一致。
- 配置说明与真实默认值一致。
- 安全文档与中间件真实行为一致。

项目内示例：
- 新增 WMV 支持不能只改前端：
  - `internal/media/scanner.go` 分类识别。
  - `internal/handler/handlers.go` 返回 `video/x-ms-wmv`。
  - 前端播放策略识别 WMV 风险。
  - 文档同步写明 WMV 的策略与边界。

## 4. 严格测试导向的改动交付

Codex 3.5 在“改动后如何证明没坏”方面价值很高。

建议默认交付标准：
- 行为变更必须伴随测试或可验证脚本。
- 至少执行：
  - `go test ./...`
  - `go vet ./...`
  - `golangci-lint run`
  - `pnpm -C web build`（涉及前端时）

项目内示例：
- 安全中间件调整后，补充 `middleware_test.go`：
  - `RemoteAddr` 提取规则。
  - 代理头忽略规则。
  - PIN 豁免路径与会话校验。

## 5. 发布工程化与文档资产化

Codex 的优势不止编码，还包括把“临时修复”沉淀成可复用发布资产。

建议做法：
- 每次关键变更都形成：
  - 版本说明（`docs/release/vX.Y.Z.md`）
  - 变更摘要（`CHANGELOG.md`）
  - Wiki 对应专题页同步（中英文）
- 发布动作标准化：打 tag -> 推送 -> 触发 `release.yml`。

项目内示例：
- 完成播放策略精修后，同步更新：
  - 主仓库 README/配置/API/安全文档。
  - Wiki 的 Home、Encoding、Configuration、Security、Release、Changelog。

## 6. 你可以优先交给 Codex 的任务清单

以下任务最值得优先交给 Codex：
- 复杂故障的系统化定位与修复（含跨层链路）。
- 低风险重构（去重复、降复杂度、补测试）。
- 版本发布前的一致性清理（代码-配置-文档-Wiki）。
- CI/lint 失败的批量归因与收敛修复。
- 面向长期维护的文档重写与结构优化（中英文同步）。

## 7. 不建议优先交给 Codex 的任务

在本项目语境下，以下任务通常收益较低：
- 纯机械、可一键完成且无需判断的重复点击操作。
- 你本地已高度自动化且 1 分钟内可完成的可视化检查。

这类任务更适合你直接处理，Codex 更适合做“需要技术判断和跨文件一致性”的工作。
