# MSP 进化方向分析

> 基于当前架构、功能面、使用场景的深度分析。每项建议标注「场景驱动力」——不存在场景驱动的改动不提。

---

## 当前画像

| 维度 | 现状 |
|------|------|
| **定位** | 家庭局域网轻量媒体服务器——"Your Personal LAN Cinema" |
| **用户** | 1-5 人家庭/工作室，技术水平中等，NAS/HTPC 场景 |
| **媒体类型** | 视频（H.264/H.265/AV1/VC-1）、音频（含歌词、封面）、图片、其他 |
| **播放能力** | 直接播放 + FFmpeg 实时转码，HW 加速，断点续播 |
| **安全** | PIN 码 + IP 黑白名单 |
| **部署** | 单二进制 / Docker / 跨平台（Windows/Linux/macOS/loong64） |
| **前端** | PWA、Plyr 播放器、暗色/亮色主题、中英双语 |
| **版本** | v1.6.x，架构已经历 3 次重大重构，代码质量成熟 |

---

## 方向一：多设备协同播放体验

### 场景驱动力
家庭中最常见的情形：**客厅电视上看到一半，回卧室继续看；或手机上找到想看的，投到电视上**。当前只有 `PlaybackProgress` 跨设备续播（需手动点击 Resume），缺少主动的设备感知。

### 建议

| 改动 | 复杂度 | 价值 |
|------|--------|------|
| **WebSocket 实时进度同步** | Standard | 设备 A 暂停后，设备 B 打开同一文件自动提示"从 xx:xx 继续？" |
| **"正在播放"状态广播** | Standard | 顶栏或侧栏显示"客厅正在播放《xxx》" |
| ~~DLNA/投屏~~ | 过重，不建议 | 偏离"轻量"定位，且浏览器端 DLNA 不可行 |

> [!IMPORTANT]
> WebSocket 对当前纯 HTTP `net/http` 架构是增量改动（`nhooyr.io/websocket` 零依赖），不需要引入框架。且只需一个 `/api/ws` 端点，用于进度事件推送。

---

## 方向二：媒体库体验增强

### 场景驱动力
当共享目录中有 **500+ 视频文件**时，当前平铺列表 + 搜索的方式效率下降。用户需要的是「找到想看的东西」，而不是滚动浏览。

### 建议

| 改动 | 复杂度 | 价值 |
|------|--------|------|
| **文件夹层级浏览** | Standard | 当前 `WalkShares` 扁平化所有文件。增加按目录树浏览模式（保留当前扁平模式作为切换选项），电视剧分季分集自然呈现 |
| **视频缩略图** | Standard | 首次访问时 ffmpeg 截取关键帧生成缩略图，缓存到磁盘。列表从纯文本变为视觉化网格 |
| **最近播放 / 继续观看** | Light | 利用现有 `PlaybackProgress` 数据，首页增加"继续观看"区域。这是所有流媒体服务的核心入口 |
| **收藏 / 标记** | Light | SQLite 加一张表，前端加星标按钮。解决"记住想看的"需求 |

> [!TIP]
> 文件夹浏览不改 `WalkShares` 核心逻辑——在前端按 `ShareLabel` + 路径前缀分组即可实现第一版，零后端改动。

---

## 方向三：音频体验深化

### 场景驱动力
MSP 已经有相当完善的音频能力（歌词、封面、shuffle、loop、续播），说明**音频是一个被积极使用的场景**。但目前音频体验距离"家庭背景音乐播放器"还差一步。

### 建议

| 改动 | 复杂度 | 价值 |
|------|--------|------|
| **播放队列** | Light | 当前 playlist 固定为某个 scope 下的全部音频。增加"添加到队列"能力，允许跨 share 自由组合 |
| **音频可视化** | Nano→Light | `<canvas>` + Web Audio API 频谱/波形动画。纯前端改动，提升音乐播放的沉浸感 |
| **专辑/艺术家分组** | Standard | 从 ID3/Vorbis 标签提取元数据（ffprobe 已返回这些信息），按专辑/艺术家聚合 |

---

## 方向四：安全与访问控制进化

### 场景驱动力
当前 PIN 码是全局单一密码，IP 黑白名单是手动配置。对于**家里有小孩**或**与朋友临时分享**的场景，粒度不足。

### 建议

| 改动 | 复杂度 | 价值 |
|------|--------|------|
| **Share 级别 PIN** | Light | 不同共享目录设置不同 PIN。保护特定内容而不影响全局访问 |
| **临时分享链接** | Standard | 生成带过期时间的一次性 URL，可发给朋友。不需要他们知道 PIN |
| ~~用户系统~~ | 过重，不建议 | 家庭场景不需要注册/登录，违背"zero setup"定位 |

---

## 方向五：系统可观测性

### 场景驱动力
长时间运行的家庭服务器，用户想知道：**谁在看什么、转码占了多少 CPU、磁盘缓存有多大**。当前只有 `/api/log` 和控制台日志。

### 建议

| 改动 | 复杂度 | 价值 |
|------|--------|------|
| **Web 管理面板** | Standard | Settings 页面扩展为仪表板：活跃转码任务、缓存大小、最近访问记录、连接设备列表 |
| **转码进度反馈** | Light | 当前转码是黑盒流式输出。前端增加"转码中…"状态指示器，告诉用户为什么视频加载慢 |

---

## 方向六：性能与大库优化

### 场景驱动力
当共享目录包含 **10,000+ 文件**时（典型 NAS 场景），全量 `WalkShares` 耗时可观。当前有 `maxItems` 限制和 `stale-while-revalidate` 缓存，但大规模场景下仍有改进空间。

### 建议

| 改动 | 复杂度 | 价值 |
|------|--------|------|
| **增量扫描（inotify/ReadDirectoryChangesW）** | Standard | 首次全量扫描后，通过 OS 文件监控只处理变更。消除重复扫描开销 |
| **分页 API** | Light | `/api/media` 增加 `offset` + `limit` 真分页（当前 `limit` 仅用于首屏快加载）。前端实现无限滚动 |
| **SQLite 全文搜索** | Light | 利用 SQLite FTS5 索引文件名，替代前端内存过滤。大库下搜索性能从 O(n) → O(log n) |

---

## 不建议的方向

| 方向 | 原因 |
|------|------|
| **用户/账户系统** | 违背 "zero setup, no cloud account" 核心定位 |
| **DLNA/Chromecast 协议** | 实现成本极高，且 MSP 的浏览器客户端定位已覆盖跨设备访问 |
| **移动端原生 App** | PWA 已覆盖移动端，原生 App 维护成本高、收益低 |
| **在线字幕下载** | 引入外部网络依赖，违背 local-first 原则 |
| **多用户权限矩阵** | 家庭场景不需要 RBAC，会让配置变复杂 |
| **替换 Plyr 播放器** | Plyr 已深度集成且满足需求，替换成本高于收益 |

---

## 优先级建议

按「投入产出比 × 场景频率」排序：

```
1. 🟢 最近播放 / 继续观看        [Light]  — 高频场景、改动小、立竿见影
2. 🟢 视频缩略图                 [Standard] — 视觉冲击力最大的单项改进
3. 🟢 文件夹层级浏览              [Standard] — 大库可用性的关键改进
4. 🟡 转码进度反馈               [Light]  — 消除"为什么卡住了"的困惑
5. 🟡 WebSocket 实时进度同步      [Standard] — 多设备家庭的体验飞跃
6. 🟡 临时分享链接               [Standard] — 社交分享场景独有价值
7. 🔵 播放队列                   [Light]  — 音频重度用户的刚需
8. 🔵 增量扫描                   [Standard] — 大库性能的终极解决方案
```

> [!NOTE]
> 以上每项都可以独立实施、独立发版。建议按 1→2→3 的节奏推进，每个版本只做 1-2 项，保持 MSP 一贯的小步快跑风格。
